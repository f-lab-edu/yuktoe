# Feature Specification: 홈 화면 데이터 레이어 (Home Screen Data Layer)

> 본 문서는 홈 화면이 필요로 하는 **데이터 레이어의 계약**(무엇이 필요하고 어떤 약속을 지켜야 하는가)을 정의한다. 특정 백엔드 / 로컬 저장소 / 라이브러리 선택과 무관하며, 구현 방법은 [plan 문서](../plans/home_data.md)에서 다룬다.

## User Scenarios & Testing *(mandatory)*

홈 화면은 보호자(부모)가 **현재 선택된 한 아기**의 기본 정보와 양육 기록을 한 화면에서 보고, 새 기록을 남기거나 지우며, 보호자로 등록된 여러 아기 사이를 전환하도록 돕는다. 본 spec 은 그 화면을 떠받치는 데이터 레이어가 제공해야 하는 데이터와 계약을 정의한다(화면 위젯 / ViewModel 등 표시 계층은 범위 밖).

### User Story 1 — 현재 선택된 아기의 홈 데이터 보기 (Priority: P1)

보호자로서, 나는 앱을 열었을 때 현재 선택된 아기의 이름·생년 정보와 함께 최근 양육 기록, 그리고 "마지막으로 언제 먹였는지 / 기저귀를 갈았는지 / 일어났는지" 요약을 별도 조작 없이 보고 싶다. 흩어진 정보를 직접 모으지 않고 아기의 현재 상태를 한눈에 파악하기 위해서다.

**Why this priority**: 홈 화면이 존재하는 근본 이유다. 선택된 아기의 기본 정보와 기록을 제공하지 못하면 화면은 성립하지 않는다. 이 스토리만으로도 "내 아기 홈" 이라는 독립적 가치를 전달하는 MVP 가 된다.

**Independent Test**: 기록이 있는 아기를 선택해 홈에 진입하고, 기본 정보 + 기록 리스트 첫 페이지 + 카테고리별 최근 요약이 함께 채워지는지 확인하면 단독으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 보호자로 등록된 아기가 있고 그 아기에 기록이 있을 때, **When** 홈에 진입하면, **Then** 선택된 아기의 기본 정보, 기록 리스트 첫 페이지, 수유·기저귀·기상 최근 요약이 함께 제공된다.
2. **Given** 한 영역(예: 기본 정보)의 조회가 실패하고 다른 영역(예: 기록 리스트)은 성공할 때, **When** 홈을 보면, **Then** 각 영역은 서로 독립적인 성공/실패 결과로 전달되어 호출자가 영역별로 처리할 수 있다.
3. **Given** 저장된 "선택된 아기" 식별자가 더 이상 접근 불가(stale)할 때, **When** 그 아기의 기본 정보를 조회하면, **Then** "접근 불가/미존재" 임을 나타내는 구분된 오류가 반환되어 호출자가 다른 아기로 정합화할 수 있다.

---

### User Story 2 — 보호자로 등록된 아기 목록과 전환 (Priority: P1)

보호자로서, 나는 내가 보호자로 등록된 아기들의 목록을 보고 다른 아기로 전환하고 싶다. 한 계정으로 여러 아기를 돌보기 때문이다.

**Why this priority**: 어떤 아기를 보여줄지 결정하려면 후보 목록이 필요하다. 또한 stale 한 선택을 정합화할 때의 fallback 대상이기도 하다.

**Independent Test**: 둘 이상의 아기를 보호자로 둔 계정으로 목록을 조회해 생성일 내림차순으로 후보가 오는지, 다른 아기를 선택했을 때 선택 상태가 갱신·영속되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 보호자로 등록된 아기가 둘 이상일 때, **When** 목록을 조회하면, **Then** 각 아기의 식별자와 이름이 생성일 내림차순으로 반환된다.
2. **Given** 보호자로 등록된 아기가 한 명도 없을 때, **When** 목록을 조회하면, **Then** 빈 목록이 아니라 "대상 없음" 을 나타내는 구분된 오류가 반환된다(등록 화면 유도 등 다른 동작이 필요한 신호).
3. **Given** 사용자가 다른 아기를 선택할 때, **When** 선택을 확정하면, **Then** 현재 선택 상태가 그 아기로 갱신되고 로컬에 영속되어 다음 앱 실행에서 복원된다.

---

### User Story 3 — 기록 생성 / 삭제 (Priority: P2)

보호자로서, 나는 수유·기저귀·수면 등 새 기록을 남기고 잘못 남긴 기록을 지우고 싶다. 양육 활동을 기록하는 것이 앱의 일상적 사용 흐름이기 때문이다.

**Why this priority**: P1 이 "데이터를 본다" 는 가치라면 P2 는 "데이터를 남긴다/고친다" 는 가치다. P1 없이는 보여줄 것이 없지만, 기록 생성/삭제가 일상 사용을 완성한다.

**Independent Test**: 한 아기에 대해 기록을 생성하면 그 기록이 식별자·생성시각이 채워진 완전한 도메인 모델로 즉시 반환되는지, 삭제 시 대상이 없으면 "미존재" 오류로 구분되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 보호자가 새 기록 내용을 확정할 때, **When** 생성 요청을 보내면, **Then** 영속화된 뒤 식별자·생성시각까지 채워진 완전한 기록 모델이 반환되어 호출자가 그대로 리스트 맨 앞에 추가할 수 있다.
2. **Given** 이미 삭제되었거나 존재하지 않는 기록을 지우려 할 때, **When** 삭제 요청을 보내면, **Then** "미존재" 임을 나타내는 구분된 오류가 반환된다(성공으로 위장하지 않는다).
3. **Given** 네트워크 실패로 생성이 재시도될 때, **When** 같은 요청이 두 번 처리되면, **Then** 중복 기록이 생길 수 있으며(최소 1회 보장), 중복 방지는 호출자(UI)의 책임이다.

---

### User Story 4 — 기록 리스트 무한 스크롤 (Priority: P2)

보호자로서, 나는 과거 기록을 스크롤로 계속 거슬러 보고 싶다. 한 번에 모두 불러오면 느리고 불필요하기 때문이다.

**Why this priority**: 기록이 쌓일수록 페이지 단위 조회가 필요하다. P1 의 첫 페이지 가치를 확장한다.

**Independent Test**: 첫 페이지를 받은 뒤 다음 페이지 토큰으로 이어 조회해 항목이 끊김 없이 이어지고, 더 없을 때 "다음 페이지 없음" 이 전달되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기록이 한 페이지보다 많을 때, **When** 첫 페이지를 조회하면, **Then** 항목 묶음과 "다음 페이지 존재 여부 / 다음 페이지 토큰" 이 함께 반환된다.
2. **Given** 다음 페이지 토큰을 받았을 때, **When** 그 토큰으로 이어 조회하면, **Then** 호출자는 토큰 내부를 해석하지 않고 그대로 넘기기만 해도 다음 묶음을 받는다.
3. **Given** 기록이 전혀 없을 때, **When** 리스트를 조회하면, **Then** 오류가 아니라 빈 페이지(항목 없음, 다음 페이지 없음)가 성공으로 반환된다.

---

### Edge Cases

- 보호자로 등록된 아기가 한 명도 없으면 → 빈 목록이 아니라 "대상 없음" 오류로 처리한다(호출자가 등록 화면 등 다른 동작을 취하도록).
- 저장된 "선택된 아기" 식별자가 행 없음 또는 권한 차단으로 접근 불가하면 → "접근 불가/미존재" 오류로 처리하고, 호출자가 목록의 다른 아기로 정합화한다.
- 선택된 아기 식별자가 로컬에 저장되어 있지 않은 첫 실행 상태는 → 오류가 아니라 "선택 없음(null)" 정상 상태다.
- 기록이 전혀 없는 아기는 → 리스트는 빈 페이지, 카테고리별 최근 요약은 빈 목록으로 정상 반환한다(오류 아님).
- 클라이언트가 모르는 새 enum 값(기록 종류 등)을 받으면 → 그 행만 해석 실패로 거부한다.
- "진행 중" 상태의 구간 기록(시작만 있고 종료가 없는 수유/수면)은 → 데이터로 존재하지 않는다. 종료가 확정되어야 비로소 기록이 만들어진다.
- 페이지 조회 토큰의 유효기간이나 다른 아기의 토큰을 재사용했을 때의 동작은 → 정의하지 않는다(의도된 사용 흐름 안에서만 동작이 보장된다).
- 기록 생성이 네트워크 실패로 재시도되면 → 중복 행이 생길 수 있다(최소 1회 보장). 중복 방지는 호출자 책임이다.

## Requirements *(mandatory)*

### Functional Requirements

#### 아기 목록 / 기본 정보

- **FR-001**: 시스템은 현재 인증된 사용자가 **보호자로 등록된 아기들의 후보 목록**(각 항목은 식별자·이름)을 제공해야 한다.
- **FR-002**: 아기 목록은 **생성일 내림차순**("가장 최근에 추가한 아기를 가장 위로")으로 정렬되어야 한다.
- **FR-003**: 보호자로 등록된 아기가 한 명도 없으면 시스템은 **빈 목록이 아니라 "대상 없음" 오류**를 반환해야 한다(호출자가 다른 동작을 취해야 하는 신호).
- **FR-004**: 시스템은 주어진 아기 식별자에 대해 화면 표시용 **기본 정보**(식별자·이름·출생일·예정일·성별)를 제공해야 한다. 출생일·예정일은 각각 독립적으로 없을 수 있고 둘 다 없는 경우도 정상이다.
- **FR-005**: 기본 정보 조회 시 해당 아기가 현재 사용자에게 보이지 않으면(행 없음 또는 권한 차단) 시스템은 **"접근 불가/미존재" 오류**를 반환해야 한다. 호출자는 이를 저장된 선택 식별자가 stale 하다는 신호로 쓸 수 있다.
- **FR-006**: 아기 조회 메서드는 **"현재 사용자" 식별자를 인자로 받지 않아야** 한다(인증 컨텍스트에서 자동 판단). 단, 단일 아기 조회는 대상 아기 식별자를 인자로 받는다.

#### 기록 조회

- **FR-010**: 시스템은 한 아기의 기록을 **페이지 단위**로 조회해야 한다. 각 페이지는 항목 묶음, 다음 페이지 존재 여부, 다음 페이지 토큰을 포함한다.
- **FR-011**: 페이지 조회 토큰은 **호출자가 내부를 해석할 필요 없는 불투명 값**이어야 한다. 호출자는 받은 토큰을 그대로 다음 호출에 넘기기만 한다. "다음 페이지 있음" 과 "토큰 있음" 은 같은 의미다.
- **FR-012**: 기록 리스트는 **사건 시각 내림차순**으로 정렬하고, 시각이 같으면 식별자 내림차순으로 동률을 해소해야 한다.
- **FR-013**: 시스템은 페이지 크기 상한을 받아야 하며, 허용 범위(1 이상, 상한 이하) 밖의 값은 **도메인 수준에서 거부**해야 한다.
- **FR-014**: 기록이 없는 아기에 대해서는 오류가 아니라 **빈 페이지**(항목 없음, 다음 페이지 없음)를 성공으로 반환해야 한다.
- **FR-015**: 시스템은 카테고리별 **최근 N건 요약**을 제공해야 한다 — 수유(`feeding` 단일 카테고리), 기저귀, 기상(수면 종료) 각각. **유축(pumping)은 수유 요약에 포함하지 않는다.**
- **FR-016**: 카테고리별 요약의 **기준 시각**은 "그 활동이 끝난 시점" 의 자연스러운 해석을 따라야 한다 — 수유 중 모유수유(구간)는 종료 시각, 그 외 수유(분유·유축수유·이유식)는 사건 시각; 기저귀는 사건 시각; 기상은 수면 종료 시각. 각 요약은 그 기준 시각 내림차순(동률은 식별자 내림차순)으로 정렬된다. 호출자는 정렬 규칙을 몰라도 결과 순서를 신뢰할 수 있어야 한다.

#### 기록 생성 / 삭제

- **FR-020**: 시스템은 새 기록을 영속화하고, **식별자·생성시각까지 채워진 완전한 기록 모델**을 즉시 반환해야 한다(호출자가 메모리상 리스트에 그대로 반영 가능).
- **FR-021**: 기록 생성 시 **기록 생성자(createdBy)는 인증 컨텍스트에서 자동으로 채워야** 하며, 호출자가 전달하지 않는다. 기록 종류·사건 시각 등 사건 메타데이터는 모두 기록 세부 데이터 한 곳(SSOT)에서 결정된다.
- **FR-022**: 기록 생성은 **최소 1회 보장**이다 — 재시도 시 중복 행이 생길 수 있으며, 중복 방지(단일 클릭 제한 등)는 호출자의 책임이다.
- **FR-023**: 시스템은 식별자로 지정된 기록을 영구 삭제해야 한다. **존재하지 않거나 이미 삭제된 대상은 "미존재" 오류**로 구분해 반환해야 한다(성공으로 위장하지 않는다). 삭제 성공 시 반환 페이로드는 없다.

#### 선택된 아기 상태

- **FR-030**: 시스템은 "현재 선택된 아기" 식별자를 **로컬에 영속**하고, 다음 앱 실행에서 복원할 수 있어야 한다. 저장된 값이 없는 상태는 오류가 아니라 "선택 없음(null)" 정상 상태다.
- **FR-031**: 시스템은 앱 전체에서 공유되는 **"현재 선택된 아기" 상태 홀더**를 제공해야 한다. 선택을 바꾸면 메모리 값이 갱신되고 로컬에 영속되며 변경이 **stream 으로 broadcast** 되어 여러 구독자(ViewModel)가 받는다. 구독자는 구독 시점의 현재값을 동기 getter 로 읽고, 이후 변화를 stream 으로 받는다.
- **FR-032**: 로컬 저장소 래퍼는 **변경 통지 책임을 갖지 않으며**, 저장된 식별자의 의미·권한·유효성을 검증하지 않는다(그 판정은 아기 기본 정보 조회 결과의 오류 코드로 받는다).
- **FR-033**: 로그아웃 시 호출자가 현재 선택 상태를 **명시적으로 비울 수 있어야** 한다(상태 홀더가 로컬 저장된 선택까지 제거). 로그아웃 자체는 상태 홀더/저장소의 책임이 아니다.

#### 공통 계약

- **FR-040**: 모든 조회/명령 메서드는 throw 하지 않고 **결과 또는 구분된 오류**(미존재·미인증·네트워크 실패·해석 실패 등)를 반환해야 한다. 데이터 소스 원본(DB 응답 / 맵 / DTO)은 데이터 레이어 경계 밖으로 노출되지 않는다.
- **FR-041**: 모든 시각 값은 **UTC** 로 보유·표현해야 한다. 로컬 타임존 변환, D-day / D+N 등 표시용 가공은 데이터 레이어가 수행하지 않는다(표시 계층 책임).
- **FR-042**: 데이터 레이어는 **자체 상태(캐시·큐·lock)를 갖지 않아야** 하며, 따라서 동시에 호출해도 안전해야 한다(선택 상태 홀더의 메모리 보관은 예외).

### Key Entities

- **BabyListItem (아기 목록 항목)**: "어떤 아기로 전환할지" 고르는 후보 목록용 가벼운 모델. 식별자·이름만 보유한다.
- **Baby (아기 기본 정보)**: 현재 선택된 아기의 홈 상단 표시용 모델. 식별자·이름·출생일(없을 수 있음)·예정일(없을 수 있음)·성별을 보유한다. `BabyListItem` 과 같은 식별자 체계를 쓰며, 같은 식별자는 같은 아기를 가리킨다.
- **CareRecord (양육 기록)**: 기록의 공통 헤더(식별자·아기 식별자·생성자·생성시각)와 타입별 세부 데이터를 묶는 모델. **기록 종류와 사건 시각은 별도 필드가 아니라 세부 데이터 안에 있다**(SSOT — 같은 정보가 두 곳에 저장되지 않아 짝이 어긋날 수 없다).
- **RecordDetailData (기록 세부 데이터)**: 기록 종류별 세부 값을 담는 변종 집합. 각 변종은 자기 기록 종류와 "정렬·표시 기준 시각" 을 노출한다. **수유 계열(모유수유·분유·유축수유·이유식)은 `FeedingDetail` 이라는 한 그룹으로 묶여**, 그 멤버십이 타입 수준에서 강제된다(유축·간식·물·기저귀·수면은 별개). **구간 이벤트**(모유수유·수면)는 시작·종료 시각을 모두 가지며 항상 시작 < 종료이고, 종료는 없을 수 없다.
- **RecordType (기록 종류)**: 앱이 다루는 최상위 기록 카테고리(6종 — 수유·유축·수면·기저귀·간식·물). 종류 정의의 SSOT 는 백엔드이며, 클라이언트가 모르는 새 값은 그 행을 해석 실패로 거부한다.
- **FeedingType (수유 세부 종류)**: 수유(feeding) 카테고리 내부의 세부 구분(모유수유·분유·유축수유·이유식, 4종). 수유 기록은 항상 이 4종 중 하나이며, 유축(pumping)은 수유가 아니다.
- **Page (페이지)**: 페이지 단위 조회 결과. 항목 묶음(같은 타입), 다음 페이지 토큰(불투명 값, 없으면 다음 페이지 없음), 다음 페이지 존재 여부를 보유한다.

### Assumptions

- 본 spec 은 이미 기록 기능을 사용하는 보호자를 대상으로 하며, 데이터 레이어 위의 표시 계층(홈 화면 위젯 / `HomeViewModel`)은 범위 밖이다.
- 인증은 기존 앱 메커니즘을 따른다. "현재 사용자" 는 인증 컨텍스트로 자동 판단하고, "현재 선택된 아기" 판정은 호출자의 책임이다.
- 본 앱은 한 디바이스에 한 사용자만 로그인되어 있다고 가정한다(사용자 변경은 "로그아웃 → 다른 계정 로그인" 흐름이며 그 과정에서 선택이 비워진다).
- "보호자" 의 구체 권한 정의는 백엔드의 책임이고, 데이터 레이어는 "조회 결과가 곧 그 사용자가 볼 수 있는 아기/기록" 이라는 의미로만 다룬다.
- 기록 종류·성별 등 enum 의 SSOT 는 백엔드다. 백엔드가 새 값을 추가해도 클라이언트가 함께 갱신되기 전까지 그 행은 해석할 수 없다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 보호자가 홈에 진입하면 선택된 아기의 기본 정보·기록 첫 페이지·카테고리별 최근 요약이 함께 제공되며, 한 영역의 실패가 다른 영역의 제공을 막지 않는다(영역별 독립 결과 100%).
- **SC-002**: 저장된 선택 식별자가 stale 한 모든 경우, "접근 불가/미존재" 오류가 일관되게 반환되어 호출자가 다른 아기로 정합화할 수 있다(별도의 stale 전용 신호 없이 단일 오류 코드로 100% 구분).
- **SC-003**: 기록이 전혀 없거나 부족한 아기에 대해서도 오류 없이 빈/부분 상태(빈 페이지·빈 요약)를 100% 반환한다.
- **SC-004**: 기록 생성 결과는 식별자·생성시각까지 채워진 완전한 모델로 반환되어, 호출자가 추가 조회 없이 메모리상 리스트에 그대로 반영할 수 있다.
- **SC-005**: 선택된 아기를 전환하거나 앱을 재실행해도 마지막 선택이 복원되며, 선택 변경이 구독자에게 통지된다.
